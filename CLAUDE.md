# DayTrader — notes for Claude

Tool to collect, analyze and display WoW Forever auction house data. Planning stage.

- Background and findings: `docs/PLANNING.md`. Decisions: `docs/adr/`. Workflow: `docs/WORKFLOW.md`.
- Work is tracked in GitHub issues on `PonchoAndy/DayTrader`. At the start of a task, read
  the relevant issue; if the user asks "what's next?", list open issues and suggest the first
  unblocked one.
- Reference the issue in commit messages (`Refs #N`); in PR descriptions use `Closes #N`.
- Record research results in `docs/PLANNING.md`, and comment on the issue.
- When a decision is made (in an issue or chat), write an ADR in `docs/adr/` from
  `template.md`, add it to the index in `docs/adr/README.md`, and update the summary in
  `docs/PLANNING.md` section 5. Never delete an ADR; supersede it with a new one.
- Session recaps: `docs/sessions/` — read the latest one first.
- The user is not deeply technical: explain steps plainly and say where to click.
- Never commit secrets. Keys live in GitHub Actions secrets or the cloud environment's
  network secrets, never in files.

## Issue Deck (swipeable issue cards)

The user reads and replies to issues in a private claude.ai artifact:
https://claude.ai/artifact/RpKHZGqfrwCjAqB9tDBDvL

Page source and data model: `tools/issue-deck/`. It has no GitHub connection of its own; Claude keeps it in sync using the artifact database
(ArtifactData tool, same URL). When the user says "sync the Issue Deck" (or "post my Issue Deck
replies"):

1. Post replies: query collection `replies` where `status == "pending"`. For each, post
   `body` as a comment on issue `issue` (GitHub MCP `add_issue_comment`); if `close` is true,
   also close the issue as completed. If `body` is empty (the user pressed "Mark Done" with no
   text), post no comment; just close the issue. If `reopen` is true, reopen the issue
   (state open) after posting any comment. Then update the reply doc to `status: "posted"`
   (pin with `if_version`). Post the user's words unchanged, followed by the usual
   "Generated by Claude Code" footer, since Claude is the one posting.
2. Refresh issues: list all issues (open and closed) and their comments, then `set` one doc
   per issue in collection `issues`, id `i<number>`:
   `{number, title, body, state ("OPEN"/"CLOSED"), updated_at, comments: [{user, created_at, body}], syncedAt}`.
3. Set `meta/sync` to `{syncedAt: <now ISO>}`, and `meta/syncRequest` to
   `{state: "done", finishedAt: <now ISO>}` so the page's "Sync now" button resets.
Use one `batch` write where possible.

### How replies reach Claude

Pressing Send reply / Mark Done / Reopen (or Refresh) on the page hands the work to Claude at once:
- If `meta/activeSession` has a `heartbeatAt` within the last 45 minutes, the page fires that
  session's own on-demand task (`triggerId`), so an `[Issue Deck] …` turn appears in its chat.
  When you get one, run the sync above, then carry on. (Messaging via `send_message` is a
  fallback; the page seems not to be allowed to use it.)
- Otherwise the page fires the background task "Sync the Issue Deck", which wakes the long-lived
  "Issue Deck sync (background)" session (details in `tools/issue-deck/README.md`).
- `meta/route` records which route the last press took and why.

**At the start of every work session:**
1. Create an on-demand task that fires into this session (`create_trigger`, no schedule,
   default target = this session), name "Issue Deck → active work session", prompt:
   `[Issue Deck] A reply was sent or Refresh was pressed on the Issue Deck page. Run the Issue Deck sync now (CLAUDE.md, "Issue Deck" section), then continue what you were doing.`
2. Read `meta/activeSession`; if it holds an older `triggerId` from a previous work session,
   delete that task (`delete_trigger`) so they don't pile up.
3. `set` `meta/activeSession` to `{sessionId, kind: "work", triggerId, heartbeatAt: <now ISO>}`.
4. Update `heartbeatAt` whenever you run a sync or the user sends a message.
